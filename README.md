# Тестовое задание

Оптимизация ночной синхронизации покупателей и сделок из amoCRM в PostgreSQL.

Основная функция — `collect_leads_customers(is_full=True)`.

## Что было не так

Раньше при обработке каждого покупателя или сделки выполнялся поиск в `abstract_customer`: сначала по CRM ID, а затем, если запись не находилась, по логину. При объёме в 20 тысяч покупателей и 50 тысяч сделок количество таких запросов могло доходить примерно до 140 тысяч.

Также изменения сохранялись через отдельные `commit()` внутри циклов. Перед очисткой таблицы данные приходилось загружать повторно.

## Что я изменил

Перед началом синхронизации теперь загружаются все существующие записи из `abstract_customer`. По ним создаются словари для поиска по ID покупателя, ID сделки и логину. Благодаря этому для поиска не приходится каждый раз обращаться к базе данных.

Отдельно обработал ситуацию с одинаковыми логинами. Если один логин встречается у нескольких записей, он не используется для однозначного сопоставления. При обновлении записи старый логин убирается из индекса, чтобы при дальнейшей обработке не использовать уже неактуальные данные.

Если покупатель и сделка с одним логином оказались в разных записях, данные объединяются. Основной остаётся запись, найденная по ID сделки, а лишняя запись удаляется. После объединения обновляются и индексы, чтобы следующие операции учитывали новое состояние.

Обработку покупателей и сделок разделил на блоки по 500 объектов. После каждого блока вызывается `flush()`, а изменения фиксируются одним `commit()` после успешного завершения синхронизации и очистки.

Для очистки повторно используются уже загруженные ORM-объекты — перечитывать всю таблицу из базы не требуется. При этом сама очистка выполняется только после того, как успешно завершилась загрузка и покупателей, и сделок. Если во время синхронизации возникает ошибка, выполняется `rollback()`, а удаление данных не запускается.

Также учёл связанные контакты и компании у покупателей и сделок. При полной синхронизации удаляются записи, которых больше нет в CRM, в том числе сущности, в имени которых указано «удалить».

В CRM-адаптере добавил обработку ответов API, пользовательских полей и сохранение исходных данных в JSON. Адрес API и OAuth-токен задаются через переменные окружения.

## Оценка производительности

Основное сокращение касается запросов на поиск. Вместо потенциальных 140 тысяч отдельных SELECT теперь выполняется один запрос для загрузки существующих записей. INSERT, UPDATE и DELETE по-прежнему необходимы, поскольку данные нужно сохранять в PostgreSQL.
