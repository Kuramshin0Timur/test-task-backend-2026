# Тестовое задание

Оптимизация ночной синхронизации покупателей и сделок из amoCRM в PostgreSQL.
Точка входа: `collect_leads_customers(is_full=True)`.

## Что было узким местом

До изменений для каждой сущности выполнялся поиск в `abstract_customer`: сначала по CRM ID, затем при необходимости по логину. В худшем случае это давало до 140 тыс. SELECT-запросов на выгрузку из 20 тыс. покупателей и 50 тыс. сделок. Дополнительно изменения фиксировались отдельными `commit()` внутри циклов, а перед очисткой таблица читалась повторно.

## Что изменено

- Перед синхронизацией `abstract_customer` читается одним запросом. В памяти строятся индексы по ID покупателей, ID сделок и логинам. Повторные запросы поиска для каждой сущности больше не нужны.
- Логины индексируются с учётом неоднозначности: если один логин относится к нескольким разным записям, поиск по нему не выбирает произвольную запись.
- При обновлении CRM-сущности её прежние значения логина удаляются из индекса. Это не даёт использовать устаревший логин в следующих сопоставлениях.
- При совпадении сделки и покупателя в разных строках данные объединяются в строку, найденную по ID сделки. Индексы и карта ID для очистки также обновляются.
- Покупатели и сделки обрабатываются блоками по 500 объектов. Между блоками выполняется `flush()`, а `commit()` — один раз после успешного прохода и очистки.
- Новые сделки не требуют отдельного `flush()` каждая: их ID и связанные сущности учитываются после записи блока.
- Список уже загруженных ORM-объектов используется повторно при очистке. Второго SELECT всей таблицы нет.
- Очистка запускается только после полного завершения обеих CRM-выгрузок. При любой ошибке транзакция откатывается, поэтому частичная выгрузка не приводит к удалению данных.
- Вложенные контакты и компании учитываются как у покупателей, так и у сделок. Сущности с «удалить» в имени удаляются при полной очистке.
- В CRM-адаптер добавлена загрузка сущностей из API-ответа, сохранение исходного JSON и разбор пользовательских полей amoCRM. Адрес API и OAuth access token передаются через переменные окружения.

## Запросы и память

Для поиска вместо потенциальных 140 тыс. отдельных SELECT выполняется один SELECT существующих `abstract_customer`. Записи в PostgreSQL остаются необходимыми: для каждого изменённого объекта требуется INSERT или UPDATE, а при очистке — DELETE/UPDATE. SQLAlchemy может объединять совместимые операции записи в пакетные вызовы; точное число SQL-команд зависит от доли новых и существующих записей, структуры данных и драйвера PostgreSQL.

При размере блока 500 выполняется около 40 циклов `flush()` для 20 тыс. покупателей и 100 циклов для 50 тыс. сделок. Это число циклов ORM, а не гарантированное число SQL-команд. На весь успешный запуск приходится один `commit()`.

Индексы и карта ID хранятся в памяти. Для порядка 70 тыс. CRM-сущностей служебные Python-структуры могут занимать несколько десятков мегабайт (ориентировочно 40–80 МБ на типичном 64-битном CPython, в зависимости от распределения записей). Сверх этого объёма загружаются ORM-объекты и JSONB-поля существующих покупателей; их размер зависит от фактического содержимого базы и может быть основным потребителем памяти. Оценка не является замером на производственной выгрузке.

## Настройка

Перед вызовом синхронизации должны быть настроены Flask-приложение и `db` из `models.py`, включая подключение к PostgreSQL. Для CRM-адаптера задаются переменные окружения:

- `AMOCRM_BASE_URL` — базовый URL аккаунта, например `https://example.amocrm.ru`;
- `AMOCRM_ACCESS_TOKEN` — действующий OAuth access token.

Зависимости устанавливаются командой `pip install -r requirements.txt`.

## Проверки и ограничения

Локально проверены синтаксис Python и тесты преобразования ответов amoCRM в объекты. Полный прогон с PostgreSQL и реальным аккаунтом amoCRM не выполнялся: для него нужны настройки приложения, база и действующий токен. Перед эксплуатацией следует проверить сценарии на тестовой базе и замерить реальный размер загружаемых JSONB-данных.
